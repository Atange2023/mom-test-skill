# 对话流程与笔记（Running the process）

## R — 原文 (Reading)

> "Avoid creating (or being) the bottleneck. To do that, the customer and learning has to be shared with the entire founding team, promptly and faithfully."
>
> "If you don’t know what you’re trying to learn, you shouldn’t bother having the conversation."
>
> "Notes are useless if you don't look at them."
>
> — Rob Fitzpatrick, Chapter 8

**中译**：要避免制造（或成为）瓶颈——为此，客户与学习成果必须**及时、忠实**地分享给整个创始团队。如果你不知道自己想学什么，就别浪费时间做这次对话。笔记你不回头看，就毫无用处。

---

## I — 方法论骨架 (Interpretation)

即使前面都做对了，如果**流程（process）**不对，结果依然会是坏的。核心风险是**学习瓶颈**：负责谈客户的人把学习成果揣在自己脑子里，于是"我学到了什么"变成了"你要做什么"，诞生一个以"客户说了算"为终极王牌的事实上的独裁者。作者亲历的极端案例是：他一个人去谈、笔记很烂、不与团队复盘，最后 CTO 辞职说"你要是老改我们要做的东西，我们永远成不了事"。

避免瓶颈靠三件事：**会前准备（prepping）、会中笔记、会后复盘（reviewing）**。

**会前：**
- 定好本类人的**3 个大问题**，和**整个创始团队**（业务 + 产品都要在场）一起定，并刻意去面对那些吓人的问题。
- 若已有认知，还应想好结束时**要推进的承诺/下一步**。
- 写下一份"我猜这位受访者在乎什么"的最佳猜测（最多一小时）——你会猜错，但有骨架更容易把讨论引到要点。
- 能靠桌面调研回答的问题**先查掉**；见企业前花 5 分钟做 LinkedIn/官网尽调。
- 两个挖掘隐藏风险的问题：**"如果这公司失败了，最可能因为什么？"** 和 **"要让它大获成功，必须有什么为真？"**（借自 Lafley/Martin）。若时间紧，只需问一句："**我们想从这帮人身上学到什么？**"

**会中 / 与会者：**
- 决策者（含技术决策）都要**至少参加部分**会议；技术同事不必参加大多数，但偶尔亲耳听客户反应价值很大。
- **两人最佳**：一人主导、一人记录；记录者还要负责在主导者问错问题/漏掉信号时**当场补救**。别超过两人（除非是团队对团队）。独自去也行，但更难自我纠偏。
- **不能外包客户学习**：在跑通商业模式与可复制的销售/营销流程之前，创始人必须亲自在场（至少在场听）。

**会后复盘：**
- 和团队过一遍笔记、关键引言、结论与遇到的问题；也能聊"哪类问题有效、哪类无效"这种元层面——这是**手艺**，要刻意练。
- 把学习**尽快、尽量直接用笔记和原话**分享给团队，让学习落到纸面与所有人脑中。

**笔记方法：**
- 尽量记**逐字引语**（加引号），日后可用于营销文案、融资材料、平息争论；否则记"大想法"即可。
- 用**符号系统**加速记录（作者常用 12 个）：情绪（兴奋/愤怒/尴尬）、生活（痛点/目标/障碍/临时方案/背景）、具体（功能需求或购买标准/金钱或预算/提到了具体人或公司/待跟进任务）。
- 笔记要能**排序、混排、重组、与他人合并、永久可检索、且不与其他噪音混在一起**。作者的偏好是**索引卡**（一卡一条、会后补上日期和姓名，复盘时摊在桌上排序），也认可电子表格/Evernote；不建议用随手笔记本或录音（内容多但不可检索）。
- 随手记在纸巾、杯垫上也行——**回来务必转存**。

**整个流程（批次化）：**
- 会前：选好聚焦且可触达的细分 → 团队定 3 大学习目标 → （如相关）定理想下一步与承诺 → 决定该与谁谈 → 写下最佳猜测 → 能桌面调研的先查。
- 会中：设定框架 → 保持随意 → 问合规好问题 → 挡好评/拉泛泛/下挖信号 → 记好笔记 → （如相关）施压索取承诺与下一步。
- 会后：团队复盘笔记与关键引言 → 转存到永久格式 → 更新认知与计划 → 定下 3 个新大问题。
- **节奏要快**：准备只花一小时就出门；别花数月在"全职客户对话"上；作者警告不要拿方法学当拖延借口——"去建你的公司吧"。

## A1 — 应用示例 (Application Example)

### 示例 1：CTO 因学习瓶颈辞职（作者亲历，章节 8）

- **问题/输入**：作者一个人去谈客户、笔记很烂、不与团队复盘。
- **方法论的使用**：他没有把学习及时、忠实地分享给团队。
- **结论**：CTO 辞职并说"你要是老改我们要做的东西，我们永远成不了事"。
- **结果**：作者事后承认——即便他学到的东西是真的，也没用，因为他**没**把它好好传达给团队。这就是典型的"学习瓶颈"。

### 示例 2：笔记符号系统（书中示例，章节 8）

- **问题/输入**：如何在对话中高效且可检索地记录。
- **方法论的使用**：用 12 个符号给信号打标签：`:) :( :|`（情绪）、`☇`（痛点）、`⚽`（目标）、`☐`（障碍）、`⤴`（临时方案）、`^`（背景）、`☑`（功能需求/购买标准）、`＄`（金钱/预算）、`♀`（提到具体人或公司）、`☆`（待跟进）、`☑`。
- **结论**：卡片式记录让复盘时可"抽卡排序"——若发现解决的问题不重要，可直接抽出所有打了"闪电"符号的卡片，去找一个已被确认的新问题。
- **结果**：笔记变得轻量，团队**真的会去看**——这是笔记有价值的唯一前提。

### 示例 3："我们想从这帮人身上学到什么？"（书中示例，章节 8）

- **问题/输入**：时间紧、要不要做这轮对话。
- **方法论的使用**：作者说，如果时间紧迫，**问这一句就是你所需要做的全部准备工作**。
- **结论**：如果你不知道自己想学什么，就不该费劲做这次对话。
- **结果**：这成为整个流程的最小可行准备动作。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要开始（或正在）做一批用户访谈，想有一套可复用的流程。
2. 感觉团队里"谈客户"是某个人的事，其他人对一线学习毫无了解。
3. 访谈做了很多，但笔记散乱、复盘缺失、认知没更新。
4. 想知道访谈该几个人去、谁来记、记什么、怎么记。

### 语言信号 (用户的话里出现这些就应激活)

- "访谈该怎么组织 / 该谁去 / 怎么记录？"
- "我们团队对客户反馈没共识"
- "聊完就完了，没有沉淀"
- "interview process / note taking / 复盘 / 学习瓶颈"

### 与相邻 skill 的区分

- 与 `meeting-outcome-judge` 的区别：那条判定**单场会面**成败；这条是**跨会面的整体流程与知识管理**。
- 与 `question-quality-gate` 的区别：那条只管问题上；这条覆盖会前准备、人员分工、笔记与复盘。

## E — 可执行步骤 (Execution)

**必需输入**：① 本轮要谈的人群（每类人一份）；② 团队构成（谁参与、谁决策）。
**缺失处理**：若没有团队（单人创业），可把"团队复盘"降级为"个人复盘 + 笔记系统"。
**交付物与完成标准**：输出 ① 本类人的 **3 个大问题** + 1–2 条隐藏风险问题；② 会议**人员分工**（谁主导/谁记录）；③ 一份**笔记符号表**；④ 会后**复盘清单**。完成标准：五要素齐备且可立即执行。

1. **会前准备**
   - 团队（业务+产品）一起定 3 个大问题；想好要推进的承诺/下一步；写最佳猜测；先做桌面调研。
   - 完成标准：3 个问题 + 1 条"若失败会因何" + 1 条"成功必须什么为真"。

2. **确定人员与分工**
   - 两人最佳（主导 + 记录）；决策者至少参加部分会议；**不外包**客户学习。
   - 完成标准：明确谁去、谁记、谁补位。

3. **建立笔记系统**
   - 采用符号表（情绪/生活/具体三类）；尽量记逐字引语；选定可检索的载体（索引卡/表格/Evernote）。
   - 完成标准：产出一份本团队可用的符号约定。

4. **会后复盘**
   - 过检查表：关键引言、主要结论、遇到的问题、哪类提问有效。
   - 完成标准：输出复盘要记录的四项 + "更新后的 3 个新问题"。

5. **批次节奏控制**
   - 准备 ≤1 小时即出门；不要把方法当拖延借口。
   - 完成标准：写明"从准备到出门"的时间上限。

**判停条件**：若"你不知道想学什么"，停下来先定目标；若笔记没人看，先简化载体。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性的、极其轻量的随口请教——不必上完整流程。
- 已有成熟的市场研究与数据团队时（流程重心转移）。

### 作者在书中警告的失败模式

- 学习瓶颈（"你只管产品，学习交给我""因为客户这么说的！""我没时间见人，我得写代码！"）。
- 一个人去、笔记很烂、不与团队复盘。
- 笔记记在随手本或录音里，结果不可检索、自己都不看。
- 用"多聊几轮"拖延：花数月做"全职客户对话"却不动产品。
- 外包客户学习（雇人去谈，坏消息难以被真正消化）。

### 作者的盲点 / 时代局限

- 流程假设有一个**同地办公、共同决策的创始团队**；分布式/远程团队需要改造。
- 符号系统与索引卡是作者个人偏好，工具（2013 年）已过时；原则（可检索、可共享、轻量）仍成立，具体载体需替换为现代协作工具。
- "创始人必须亲自在场"在规模化组织里难以维持，需要制度化的替代机制。

### 容易混淆的邻近方法论

- 用户研究方法论中的"研究运营（research ops）"：更重规范化与研究伦理；本卡更轻、更强调"创始人亲手做"。
